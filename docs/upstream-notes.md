# Upstream KMCLib: snapshot, license and syncing

`third_party/KMCLib/` is a **git subtree snapshot** of
[leetmaa/KMCLib](https://github.com/leetmaa/KMCLib). The currently pinned commit can be looked up
with the command below (it also prints the sync and review commands):

```bash
uv run python scripts/upstream_info.py
```

Current value: `747ff805fd32308fd4b5e8d893bf58ad8670a814` (2020-12-29; upstream has 458 commits in
total, and the whole tree is about 3.5 MB).

## 1. Why a subtree rather than a submodule

| Aspect | submodule | **subtree (this repository)** |
| --- | --- | --- |
| Self-contained sdist (PyPI / conda-forge both build from the sdist) | ❌ scikit-build-core does not run `git submodule update`, so the sdist contains an empty directory | ✅ The sources are in the tree |
| The upstream build has to be reworked (mpiflag.h, md5, -Werror) | ❌ Changes would live in the submodule working tree → dirty, easily lost | ✅ All changes live in `cxx/` |
| Tracking upstream by commit hash | ✅ gitlink | ✅ Every sync commit records `git-subtree-split: <sha>` |
| Reviewing "what did this sync change" | ⚠️ After moving the gitlink, no content diff is visible | ✅ One sync = one patch |
| Fresh clone / ZIP download / sandboxed CI / conda sandbox | ❌ Needs an extra initialization step | ✅ No special cases |
| Per-commit upstream `git log`/`blame` | ✅ | ❌ Unless `--squash` is dropped when syncing |

Upstream stopped being updated after 2020, so the actual sync frequency is ≈ 0. "One reviewable
patch per sync + the recorded commit hash" is therefore more useful than "458 upstream commits
mixed into this project's history".

## 2. Syncing upstream

```bash
# Pull the latest commit of upstream master (one sync = one squash commit)
git subtree pull --prefix=third_party/KMCLib https://github.com/leetmaa/KMCLib.git master --squash

# Review the changes this sync brought in
git log -1 --format=%B                      # the commit message lists the upstream commit hashes and subjects in <old>..<new>
git diff HEAD^1 HEAD -- third_party/KMCLib  # content changes

# To browse the upstream commits one by one (needs network access)
git fetch https://github.com/leetmaa/KMCLib.git master
git log --oneline <old SHA>..FETCH_HEAD
```

If you decide that upstream commits should enter this repository's history unchanged (so that
`git blame` keeps the original authors), just drop `--squash`. The rest of the design is unaffected;
the cost is that 458 upstream commits will show up in `git log`.

## 3. Freeze rules

1. **Do not edit any file under `third_party/KMCLib/`.** All build adaptation lives in `cxx/`:
   - `mpiflag.h` is generated from `cxx/mpiflag.h.in` into the build directory (upstream writes it
     back into the source tree);
   - md5 is extracted from `c++/externals/zip/md5.tar.gz` at build time (see §4);
   - compiler options, the C++ standard and the pybind11 bindings are all in `cxx/CMakeLists.txt`
     and `cxx/bindings/`.
2. CI checks this: `git status --porcelain third_party/KMCLib` must be empty.
3. The upstream Python front end in `src/pykmclib/` is generated by `scripts/gen_python_layer.py`
   from `third_party/KMCLib/python/src/KMCLib`, rewriting `KMCLib → pykmclib`; CI verifies with
   `--check` that there is no drift. Hand-written files (`__init__.py`, `Backend/Backend.py`,
   `Backend/Custom.py`) are not overwritten. `--check` also fails on any other `.py` file in
   `src/pykmclib/` that has no upstream counterpart, so a new hand-written module must be added
   to the `OURS` list in the script.

## 4. md5

Upstream keeps its MD5 implementation in `c++/externals/zip/md5.tar.gz` (3.4 KB, containing
`md5/{md5.h,md5.c}`), and `hash.cpp` references it with `#include "externals/md5.h"`. At build time
CMake extracts it into the build directory and copies it to `externals/md5.h` and `externals/md5.c`
to satisfy that include path.

**`md5.c` must be compiled as C++**: upstream `hash.cpp` has no `extern "C"`, so it links against
the C++-mangled `MD5_*` symbols; compiling it with a C compiler fails at `import` time with
`symbol not found in flat namespace '__Z10MD5_Update...'`.

## 6. Why the upstream build system is not used

Upstream `c++/CMakeLists.txt`:

- `cmake_minimum_required(VERSION 2.8)` — rejected outright by CMake ≥ 4;
- uses the `cmake_force_cxx_compiler` module, which was removed in CMake 3.6;
- global `-Werror -pedantic`, which makes 2016-era code almost certain to fail on modern clang/MSVC;
- `file(WRITE …/src/mpiflag.h …)` and `wrap/custom.i` write generated files back into the **source
  tree**, which fails in read-only source directories (unpacked sdist, conda build sandbox,
  `pip install --no-build-isolation`).

The `CMakeLists.txt` files in those directories are kept only as a record of provenance and take no
part in the build.
